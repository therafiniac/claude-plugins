# Capability: File storage
Kind: capability
Ask when: users upload files (avatars, documents, images), or the app stores files it generates (exports, invoices, reports). Images that ship with the code are assets, not this concern.
Default: frameworks with a server (nextjs, react-express, astro on-demand routes) → cloudflare-r2. Existing AWS account or a need for AWS-only features → aws-s3. Static output → skip.
Verified: drafted November 2026, not yet re-verified option by option. Verify the chosen option in its official docs before scaffolding.

## Options
| Option | Status | Pick when | Works with | Cost |
|---|---|---|---|---|
| cloudflare-r2 | adopt | Default object storage. S3-compatible API, no egress fees | nextjs, react-express, astro (on-demand routes) | free tier; then storage and operations priced |
| aws-s3 | adopt | The project already uses AWS, or needs AWS features (event notifications to Lambda, object lock) | nextjs, react-express, astro (on-demand routes) | pay for storage, requests, and egress |
| uploadthing | trial | Next.js or React app that wants a hosted upload flow with typed routes and ready UI components | nextjs, react-express | free tier; paid plans |
| local-disk | hold | Never for user uploads in production. Container disks are often wiped on redeploy, do not scale past one instance, and serve files from the app's own origin | any | free |

## Option: cloudflare-r2
Setup: `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner`. Create a private bucket and an API token scoped to that bucket only. The client uses `region: 'auto'` and the account's R2 endpoint. Env (server-only, validated): `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`. For public files (only if the spec says so), a custom domain on the bucket, never the `r2.dev` URL in production. Configure CORS on the bucket for direct browser uploads from your origin only.
Conventions:
- One `storage.ts` module wraps the client: `createUploadUrl`, `createDownloadUrl`, `deleteObject`, `headObject`. No other file imports the SDK.
- Direct browser upload with a presigned PUT URL: sign the content type and content length, expire within minutes.
Security checks (added to security-audit):
- The API token is scoped to one bucket with only the permissions used (§5, §10).
- Bucket CORS allows only the app's origins and the methods used (§7).
Sources: https://developers.cloudflare.com/r2/api/s3/api/, https://developers.cloudflare.com/r2/api/s3/presigned-urls/

## Option: aws-s3
Setup: `@aws-sdk/client-s3` and `@aws-sdk/s3-request-presigner`. A private bucket with Block Public Access on, default encryption, and an IAM user or role whose policy allows only the needed actions on that bucket's prefix. Env (server-only, validated): `AWS_REGION`, `S3_BUCKET`, plus credentials from the host's secret settings or role. Public files through CloudFront, not public buckets.
Conventions:
- One `storage.ts` module wraps the client: `createUploadUrl`, `createDownloadUrl`, `deleteObject`, `headObject`. No other file imports the SDK.
- Presigned POST with a `content-length-range` condition when the size must be enforced at upload time.
Security checks (added to security-audit):
- Block Public Access is on; the IAM policy is limited to the bucket and actions used (§5, §10).
Sources: https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html, https://docs.aws.amazon.com/AmazonS3/latest/userguide/access-control-block-public-access.html

## Option: uploadthing
Setup: `uploadthing` and `@uploadthing/react`. Env: `UPLOADTHING_TOKEN` (server-only). Define file routes with size and type limits and a middleware that authenticates the user.
Conventions:
- Every file route's middleware checks the session and returns the user ID; `onUploadComplete` stores the file key against that user.
Security checks (added to security-audit):
- Every file route authenticates in its middleware and sets explicit size and type limits (§7, §3).
- The privacy notice names the service as a processor (§11).
Sources: https://docs.uploadthing.com/

## Shared
Conventions:
- Flow: the client asks the server for an upload URL → the server authenticates, authorizes, validates the declared type and size, and creates a pending record → the client uploads directly to storage → the client confirms → the server checks the object (size, type by magic bytes) and marks it ready.
- Object keys are generated by the server (`<owner-id>/<uuid>`). The user's filename is stored only as sanitized metadata.
- Buckets are private by default. Downloads use short-lived presigned GET URLs issued after an ownership check, or go through an authorized route.
- Images are re-encoded on the server (for example with `sharp`), which strips EXIF location data and normalizes the format.
- A lifecycle rule or scheduled job deletes pending uploads that were never confirmed.
- Deleting a record deletes its object (or schedules it), so storage holds no orphaned personal data.
Security checks (added to security-audit):
- Size and type limits are enforced server-side; type is checked by content, not extension or the client's `Content-Type` (§7).
- Every download URL is issued after an ownership or permission check on that specific file (§3).
- User files are served from a separate domain from the app, with `X-Content-Type-Options: nosniff`, and `Content-Disposition: attachment` for anything that is not an image (§7, §12).
- SVG and HTML uploads are rejected, or served only as attachments (§7).
- If users share files with other users, malware scanning is in place or marked Needs manual verification (§7).
Performance checks (added to performance-audit):
- Images are resized to the sizes the UI shows and served with long cache headers through a CDN (§5).
- Uploads go directly to storage, never through the app server's memory (§7).
Accessibility checks (added to accessibility-audit):
- The upload control is a real file input or a button that opens one, with a label, keyboard access, and announced progress and errors (§3, §5).
